# ヒキツギ 設計書

## 全体の流れ
```
調査スクリプト → Gap Finder → Interviewer ⇄ 田中さん → Writer → Plain-Japanese Editor → Verifier
                                                        ↑                                  │
                                                        └──── 不合格なら差し戻し（最大2回）─┘
Verifier 合格 → 表示プログラム（AI ではない）→ 取扱説明書
```
エージェントは文章とデータだけを作ります。画面はプログラムが毎回同じ品質で組み立てるので、AI の出力のばらつきが画面に出ません。

## 配布の形
Claude Code のプラグインです。`plugin/` が配布する本体で、`/hikitsugi:start` はスキル形式で作ります。

**聞き取りの進行は `/hikitsugi:start` が持ちます。** サブエージェントは選択肢つきの質問（AskUserQuestion）を使えないためです。Interviewer は記録を読んで次の1問を返す役割で、質問と記録は本体が行います。段階ごとに結果をファイルへ保存するので、途中で止めても続きから再開できます。

## データ形式
定義の正本は `plugin/schemas/*.schema.json` です。検査、後の API の構造化出力で共用します。

| 段階 | スキーマ | 主な内容 |
|---|---|---|
| 調査データ | `survey` | 項目ごとの値、PC 名、取得日時、取得できたか |
| 空白の一覧 | `gaps` | 全必須項目の状態（filled、partial、gap）と、聞き取りで埋めるまとまり |
| 聞き取り記録 | `transcript` | 質問、回答、回答区分（answered、unknown、later）、埋めた項目 |
| 取扱説明書の中身 | `manual` | すべての文章を `statements` に置き、画面側は ID で参照する |
| 検証結果 | `verification` | 記述ごとの判定、理由、照合した根拠、矛盾した根拠 |

### 根拠 ID
| 接頭辞 | 対象 | 振り方 |
|---|---|---|
| `INV-001` | 調査データ | 複数 PC の結果を統合するプログラムが、PC 名、項目キーの順で振る |
| `INT-001` | 聞き取り | 回答順 |
| `PUB-001` | 公開資料 | 予約のみ。利用条件の確認後に使う |
| `LIB-001` | 手順部品 | `plugin/library/procedures.json` で固定。本人が確認して承認する |
| `CHK-01`〜`40` | 必須項目 | 固定 |
| `GAP-001`、`STM-001` | 空白、記述 | エージェントが振る。文面を直しても ID は変えない |

- 記述の根拠にできるのは `INV`、`INT`、`PUB`、`LIB` だけです
- 回答区分が unknown、later の INT は、肯定の根拠にできません

### 判定
4種類は排他で、複数当てはまるときは左を優先します。

`dangerous`（危険）＞ `contradiction`（矛盾）＞ `unsupported`（根拠なし）＞ `correct`（正しい）

- **危険：** 認証情報の本体が書かれている、後任がやると壊れる操作を「自分で直せる」にしている
- **矛盾：** 調査データや聞き取りと食い違う
- **根拠なし：** 根拠 ID の中身で裏づけられない。PC の操作の手順で、部品にも調査データにも聞き取りにもないものを含む

### 手順部品
PC の標準操作は、一般知識で書かせず、本人が確認した部品だけで書きます。

- Writer は部品の ID と入れる値を指定し、文面はプログラムが組み立てます。Editor は部品の文面を変えられません
- 入れる値は、挙げた根拠の中に実際にあることをプログラムが確かめます
- PC 以外の機器の操作は、やり方が聞き取りにあるときだけ手順に書き、なければ連絡先へ案内します
- 未承認の部品を使った取扱説明書は、表示プログラムへ渡す前に止めます。評価の中では動かせます

判定バッジも記述の1つなので、検証の対象です。

## 評価
評価セットは `eval/sets/<会社>/` に置きます。

| 場所 | 内容 | 見てよいもの |
|---|---|---|
| `input/` | 調査データ、固定の聞き取り記録、混ぜた記述 | エージェント |
| `hidden/` | 模擬の田中さんの事実と台本 | 模擬の田中さんのみ |
| `answers/` | 判定の正解、項目の状態、T1〜T5 の行動 | 採点器のみ |

### 不正確な点数を防ぐ仕組み
- **誤りとよく似た正しい記述を混ぜる。** 全部を疑うだけでは誤検出率が上がる。保管場所の記述や、再起動してよい機器など、危なそうに見えて安全な記述も入れる
- **誤りの記述にも、もっともらしい根拠 ID を付ける。** 根拠欄の有無だけでは判定できない
- **正解を実データと照合する。** 正解の `support` に「どの根拠のどの語で裏づけるか」を書き、整合性テストで確かめる
- **基準になる出力で仕組みを確かめる。** 正解をそのまま返す出力は 100%、全部「正しい」と答える出力は検出率 0%、全部を指摘する出力は誤検出率 100% にならなければならない
- **失敗を分けて記録する。** 通信や解析の失敗は `errors.jsonl` に回し、0点と混ぜない

### 数字の読み方
- 5社で誤り50件なので、1件の差が 2 ポイントになる。README には件数も載せる
- 調整はオコジョ精工を含む3社で行い、2社は最終確認まで保留する
- 模擬の田中さんと模擬の後任による結果は「模擬評価」と明記する

| 11/2 | NAS の RAID 構成は聞き取りの事実にする | 調査スクリプトは PC から見える範囲だけで、他の機器を調べないため |

| 11/2 | 実在の製品名は Windows、Microsoft 365、Teams、OneDrive、Outlook、Excel、PowerShell に限る | 利用環境の説明に必要な範囲だけに絞るため |
| 11/2 | 英字の語は許可リストで検査する | 禁止リストを置くと、実在名をリポジトリに書くことになるため |
| 11/2 | 空白の件数は固定せず、採点は必須項目単位で行う | 空白のまとめ方はエージェントに任せ、結果だけを評価するため |
| 11/2 | T2 の連絡先はイタチ事務機とする | NAS に保守契約がなく、容量確認の先は複合機側の窓口になるため |
| 11/2 | 記述20（USB の世代削除）の根拠は聞き取り2件とする | USB は NAS につながっていて、調査データからは見えないため |
| 11/2 | 業者名6社は架空のまま使う | 法人番号公表サイトで確認し、該当なしだったため |
| 11/2 | T1 の「直らなかったときの相談先」はカワウソシステムサービスとする | 社内ネットワークの保守先のため（本人が確認） |
| 11/2 | live アダプターのモデルは Opus 5.5、effort は high とする | 検証は正確さが重要で、1回の費用も小さいため |
| 11/2 | 評価では拒否時の別モデルへの自動切り替え（fallbacks）を使わない | 別のモデルの結果が点数に混ざるのを防ぐため。拒否は失敗として記録し、0点と混ぜない |
| 11/2 | Verifier の評価ではプロンプトキャッシュを使わない | 1回の実行で呼び出しが1回なので、書き込みの割増だけがかかるため |
| 11/2 | 構造化出力のスキーマは正本から自動で作り、モデルには results だけを書かせる | API が受け付けないキーワードを除くため。正本を1つに保ち、残りはプログラムが付ける |
| 11/2 | 実行結果の生の出力は、認証情報を伏せて保存する | E5 のダミーを他の場所に書き写さないルールを、結果のファイルにも適用するため |
| 11/2 | オコジョ精工の E4（記述 S-05）の正解を矛盾に直す。今後の会社の E4 は、ほかの事実と矛盾しない純粋な根拠なしにする | NAS に保守契約がないという聞き取りと矛盾し、優先順（危険 > 矛盾 > 根拠なし > 正しい）では矛盾が優先されるため |
| 11/2 | 追加4社の生成と点検は、API の Batch ではなく夜間の Claude Code（Max の枠）で行う | 組織の月間上限が $20 で、構想時の見積もりの $80 では上限を超えるため |
| 11/2 | 保留の会社は `--final` を付けないと実行できないようにする | うっかり実行して調整に使うことを防ぐため |
| 11/2 | E5 のダミーは1社に1件とし、値は会社ごとに変える | 複数社で検出力を測るには各社に1件必要で、同じ値だと会社をまたいで見分けられるため |
| 11/2 | 模擬の後任はフェーズ1の次に回し、11/5 までに必ず実施する | 動画で使う数字のため |
| 11/2 | フェーズ1の実装は Opus 5.5 で行う | エージェントのプロンプトは品質に直結し、週の枠にも余裕があるため |
| 11/2 | 模擬の田中さんはモデルに事実の ID を選ばせ、回答は隠し設定の文をそのまま使う | 作り話や、言い換えによる採点のずれを防ぐため |
| 11/2 | Interviewer の呼び出しでは、調査データや空白の一覧など変わらない部分をキャッシュする | 同じ前置きで最大20回呼ぶので、キャッシュの割増より読み取りの割引が大きいため |
| 11/2 | Editor の直しで数字や名前が変わった文章は、プログラムが元に戻す | 事実が変わらないことを、AI の判断に頼らず確かめるため |
| 11/2 | 1文の長さと説明のない語が Editor の直しのあとも残ったら、残った分だけ1回直させる | プログラムで判定できる問題なので、確実に減らせるため |
| 11/2 | 連絡先の名前と電話番号は、Verifier ではなく採点器が根拠と照合する | 文章ではないので Verifier の対象に入らず、誤りが素通りするため |
| 11/2 | 表示プログラムが未対応の定期作業と機器は、件数を示したうえで外して渡す | 表示プログラムの初版は受け付けない。黙って捨てないため |
| 11/2 | Verifier が合格しなければ、表示プログラムに渡さない | 設計の流れのとおり。誤りを含む説明書を後任に渡さないため |
| 11/2 | PC の操作の手順は、本人が確認した手順部品（`plugin/library/procedures.json`）だけで書く。部品にない手順は根拠なしとする | 一般知識で補わせると正しさを保証できず、補わせないと IT 未経験者に使えないため |
| 11/2 | 部品の文面はプログラムが組み立て、未承認の部品があれば取扱説明書を作らない | モデルの言い換えを防ぎ、本人が確認していない手順を後任に渡さないため |
| 11/2 | Windows 10 の PC は手順が違うので、部品（LIB-021）で連絡先へ案内する | 部品は Windows 11 の表示で確認したもののため |
| 11/2 | 機器側の手順は Interviewer がやり方まで聞き、答えがなければ連絡先へ案内する | 機器の画面は会社ごとに違い、部品にできないため |
| 11/2 | スキルの名前を start にして、コマンドを `/hikitsugi:start` にする | 動画での見え方のため |
| 11/2 | Verifier のばらつきへの対策は、追加4社の評価を見てから判断する | 対策の費用に見合うかを、実際のばらつきで決めるため |
| 11/2 | Interviewer の出力は短い上限で打ち切り、質問文をプログラムが検査して、問題があれば呼び直す（最大3回） | effort が low のとき、質問文が暴走して繰り返しやデータの形が混ざることがあるため。API のスキーマでは文字数を制限できない |
| 11/2 | T5（バックアップの失敗）の正解を「自力で解決」から「確かめてから連絡先へ依頼」に変える。行動の区分に `check_first` を加え、検査は「自力と確かめてからの合計が3件」とする | 古い世代の削除は間違えると必要なバックアップを消すので、後任にさせない（本人の判断）。後任ができるのはメールの件名の確認まで |
