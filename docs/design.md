# ヒキツギ 設計書

## 全体の流れ
```
調査スクリプト → Gap Finder → Interviewer ⇄ 田中さん → Writer → Plain-Japanese Editor → Verifier
                                                        ↑                                  │
                                                        └──── 不合格なら差し戻し（最大2回）─┘
Verifier 合格 → phrase-writer（探すための言い方）→ 前任者の確認（全ページ）→ 表示プログラム（AI ではない）→ 取扱説明書
完成後の更新は同じ入口から。直す部分だけ Writer、Editor、Verifier を通し、確認した人を記録する
```
エージェントは文章とデータだけを作ります。画面はプログラムが毎回同じ品質で組み立てるので、AI の出力のばらつきが画面に出ません。

## 配布の形
Claude Code のプラグインです。`plugin/` が配布する本体で、`/hikitsugi:start` はスキル形式で作ります。

**聞き取りの進行は `/hikitsugi:start` が持ちます。** サブエージェントは選択肢つきの質問（AskUserQuestion）を使えないためです。Interviewer は記録を読んで次の1問を返す役割で、質問と記録は本体が行います。段階ごとに結果をファイルへ保存するので、途中で止めても続きから再開できます。

## データ形式
定義の正本は `plugin/schemas/*.schema.json` です。検査、後の API の構造化出力で共用します。

| 段階 | スキーマ | 主な内容 |
|---|---|---|
| 調査データ | `survey` | 項目ごとの値、PC 名、取得日時、取得できたか |
| 空白の一覧 | `gaps` | 全必須項目の状態（filled、partial、gap）と、聞き取りで埋めるまとまり |
| 聞き取り記録 | `transcript` | 質問、回答、回答区分（answered、unknown、later）、埋めた項目 |
| 取扱説明書の中身 | `manual` | すべての文章を `statements` に置き、画面側は ID で参照する |
| 検証結果 | `verification` | 記述ごとの判定、理由、照合した根拠、矛盾した根拠 |

### 根拠 ID
| 接頭辞 | 対象 | 振り方 |
|---|---|---|
| `INV-001` | 調査データ | 複数 PC の結果を統合するプログラムが、PC 名、項目キーの順で振る |
| `INT-001` | 聞き取り | 回答順 |
| `PUB-001` | 公開資料 | 予約のみ。利用条件の確認後に使う |
| `LIB-001` | 手順部品 | `plugin/library/procedures.json` で固定。本人が確認して承認する |
| `CHK-01`〜`40` | 必須項目 | 固定 |
| `GAP-001`、`STM-001` | 空白、記述 | エージェントが振る。文面を直しても ID は変えない |

- 記述の根拠にできるのは `INV`、`INT`、`PUB`、`LIB` だけです
- 回答区分が unknown、later の INT は、肯定の根拠にできません

### 判定
4種類は排他で、複数当てはまるときは左を優先します。

`dangerous`（危険）＞ `contradiction`（矛盾）＞ `unsupported`（根拠なし）＞ `correct`（正しい）

- **危険：** 認証情報の本体が書かれている、後任がやると壊れる操作を「自分で直せる」にしている
- **矛盾：** 調査データや聞き取りと食い違う
- **根拠なし：** 根拠 ID の中身で裏づけられない。PC の操作の手順で、部品にも調査データにも聞き取りにもないものを含む

### 手順部品
PC の標準操作は、一般知識で書かせず、本人が確認した部品だけで書きます。

- Writer は部品の ID を指定し、文面はプログラムが組み立てます。Editor は部品の文面を変えられません
- 部品に会社の値は入りません。値は「この症状で使う会社の情報」の表に置き、値が文章の根拠にあることをプログラムが確かめます
- 部品ごとに、置いてよいページの項目（まずこれだけ、手順、ゴール、分岐、例外）が決まっています
- PC 以外の機器の操作は、やり方が聞き取りにあるときだけ手順に書き、なければ連絡先へ案内します
- 未承認の部品を使った取扱説明書は、表示プログラムへ渡す前に止めます。評価の中では動かせます

判定バッジも記述の1つなので、検証の対象です。

## 評価
評価セットは `eval/sets/<会社>/` に置きます。

| 場所 | 内容 | 見てよいもの |
|---|---|---|
| `input/` | 調査データ、固定の聞き取り記録、混ぜた記述 | エージェント |
| `hidden/` | 模擬の田中さんの事実と台本 | 模擬の田中さんのみ |
| `answers/` | 判定の正解、項目の状態、T1〜T5 の行動 | 採点器のみ |

### 不正確な点数を防ぐ仕組み
- **誤りとよく似た正しい記述を混ぜる。** 全部を疑うだけでは誤検出率が上がる。保管場所の記述や、再起動してよい機器など、危なそうに見えて安全な記述も入れる
- **誤りの記述にも、もっともらしい根拠 ID を付ける。** 根拠欄の有無だけでは判定できない
- **正解を実データと照合する。** 正解の `support` に「どの根拠のどの語で裏づけるか」を書き、整合性テストで確かめる
- **基準になる出力で仕組みを確かめる。** 正解をそのまま返す出力は 100%、全部「正しい」と答える出力は検出率 0%、全部を指摘する出力は誤検出率 100% にならなければならない
- **失敗を分けて記録する。** 通信や解析の失敗は `errors.jsonl` に回し、0点と混ぜない

### 数字の読み方
- 5社で誤り50件なので、1件の差が 2 ポイントになる。README には件数も載せる
- 調整はオコジョ精工を含む3社で行い、2社は最終確認まで保留する
- 模擬の田中さんと模擬の後任による結果は「模擬評価」と明記する
