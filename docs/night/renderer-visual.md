# 長時間の作業：画面の作り直し

あなたは「ヒキツギ」の表示プログラムの担当です。依頼者はほかの作業をしていて、質問には答えられません。判断に迷ったら、安全で小さい方を選び、報告書に書いてください。**時間をかけてかまいません。審査員の記憶に残る作品に仕上げてください。** 最初に `CLAUDE.md`、`docs/design.md`、`docs/design/visual-spec.md` を読んでください。

## 作るもの
`docs/design/visual-spec.md` の第3〜9章のとおりに、`plugin/renderer/` を作り直します。**この仕様が正です。** 入力の形（`plugin/schemas/manual.schema.json`）は変えません。AI を使わず、同じ入力から毎回同じ出力を作ります。

- 入力の見本：`test/fixtures/manual-full.json`
- スマホ：下部タブ、1画面ずつ
- 2列（768〜1199px）と3列（1200px 以上）：上部バーとナビ。下部タブは出さない
- 「はじめに」の画面、確認の角印（SVG）、フッターのオコジョのシルエット（**新しく描く SVG**。白い体と黒い尾先。16px）
- 8つの部品（第7章）、手順ページの3部構成（第5章）、JavaScript なしで成り立つ動き（第9章）

## 仕様と違えるところ（本人の決定）
仕様を読むときに、次のとおりに読み替えてください。

| 仕様の箇所 | こうする | 理由 |
|---|---|---|
| 5-2、7-3「右の表」「一覧の接続先」 | 使わない。文面は手順部品のとおり「会社の情報の表」 | 表の位置はスマホと PC で違う。部品の文面は本人が承認済み |
| 8-1「◎ 手順は人が確認したものだけ載せています」 | 使わない。その場所に、確認済みのときだけ次の文を置く：「この取扱説明書は、AIがもとの情報と照らし合わせ、前任の<確認した人>さんが全ページを確認したものです。」 | 事実に合わせるため |
| 2-D、8-1 の角印「確認 / 11.05」 | `manual.review` があるときだけ、「<確認した人> 確認 <日付>」の角印を出す | 前任者の確認が済むまでは「確認済」と言えない |
| （追加）確認の前 | `manual.review` がないあいだは、上部に「下書き（前任者の確認前）」の帯を出し、角印と確認の文を出さない | 同上 |
| 8-3「この手順は確認済みです。」 | 確認済みなら「この手順は、前任の<確認した人>さんが確認済みです。」、前なら「この手順は、前任者の確認前です。」（今の表示プログラムのとおり） | 同上 |

| 3-1、6-2、7-3 の 12px と、4-2 のグループ見出しの 13px | 文字は 14px 以上。13px はタブのラベルと社外秘のチップだけ。「いまここ」は 14px、社外秘のチップは 13px、グループ見出しは 14px | 本人の決定 |
| 冒頭の「16px 以上」 | 第6章の表の値に従う（副次 15px、ラベル 14px） | 第6章が具体的なため |

## 仕様に書かれていないこと
- **① がないページ、手順がないページ：** 今の表示プログラムのとおりに番号を詰めます。① がなければ手順の見出しは「やること」、手順がなければ連絡先の見出しは「連絡してください」か「相談してください」です。ページにある部の順に、丸数字を ① から振ります
- **操作が1つもないページ（本人の決定）：** ① が空のページは `.first` の枠を出しません。空の枠や「まずこれだけ」の見出しも出しません。そのページでは **③ の連絡先を主役** にします。連絡先のカードと電話ボタンを、題名、判定、安心の帯のすぐあとに置き、説明（`notes`）はそのあとにします。第1章の「画面ごとの主役」は、手順ページなら「まずこれだけ」、① がないページなら連絡先です。毎回の見直しの画面に、このページを入れてください
- **見出しの丸数字：** ①②③ は文字のまま「① まずこれだけ」のように書きます（画面で囲みを足すのはかまいません）。「まずこれだけ」の見出しは 7-4 のとおり `.first-kicker`（15px）、② と ③ の見出しは `.part-title`（22px）です
- **説明（`notes`）：** 見出し「先に知っておくこと」で、① のあと、② の前に置きます。手順がないページでは主な内容になるので、読みやすくしてください
- **`--ink-3` は `--card` と `--bg` の上でだけ使います。** `--card-2`（4.34）と `--accent-soft`（4.48）の上では 4.5 に届きません。済んだ手順を「いまここ」の面に重ねないでください
- **PC で手順ページを選んでいないとき：** 中央の列に、一覧の説明文（いま困っていることを押してください）を出します。手順ページを勝手に開きません
- **右の列の見出し：** 4-2 の「この症状の情報」ではなく、本文と同じ「この症状で使う会社の情報」にします。手順が「会社の情報の表」と指すためです

## 手順の作業のしかた
1. HTML を作る：`node plugin/renderer/render.mjs test/fixtures/manual-full.json night-logs/manual-full.html`
2. 撮影して検査する：`node scripts/screenshots.mjs night-logs/manual-full.html night-logs/screenshots`
3. **`night-logs/screenshots/phone/` と `night-logs/screenshots/pc/` の PNG を Read で開いて、自分の目で確かめます。** 仕様の該当の章と見比べて、違いを直します。少なくとも次の画面を毎回見ます：はじめに、困ったとき、共有フォルダのページ（全部品がある）、手順のないページ、連絡先、毎月やること、会社のIT。ライトとダークの両方です
4. **1〜3 を最低3回繰り返します。** 回ごとに、見つけて直したことを報告書に書きます。「主役が1つに決まっているか」（一覧はバッジ、手順ページは「まずこれだけ」、連絡先は電話ボタン）、「暖色が押す場所だけに使われているか」を毎回確かめてください
5. 最後に `tablet/` も見ます

## 合格条件
- `npm test` が全件成功すること。約束は `test/renderer-visual.acceptance.test.mjs`、`test/renderer-full.acceptance.test.mjs`、`test/renderer.acceptance.test.mjs` の冒頭にあります
- `node scripts/screenshots.mjs` が問題なしで終わること
- `node scripts/check-secrets.mjs` が「問題なし」と出ること

## 守ること
- 変更してよいのは `plugin/renderer/`、`docs/night/renderer-visual-report.md`、`night-logs/` だけ。**`test/`、`eval/`、`scripts/`、`plugin/` のほかの場所、`package.json`、`CLAUDE.md`、`docs/design/visual-spec.md` を変更しない**
- テストが厳しすぎると思っても、弱めない。通せなければ、理由を報告書に書いて止まる
- 記述の本文と部品の文面を書き換えない。画面の固定の文言は、IT の知識がなくても分かる日本語にする
- push しない。ブランチを切り替えない。API、ネットワーク、外部ライブラリ、外部のフォントや画像を使わない。既存のアプリのデザインに似せない
- 実在の製品名やメーカー名を、CSS やコメントに足さない。例外は仕様の第6章で指定されたフォント名だけ
- コメントは日本語

## コミットのしかた
動く単位でコミットします。**コマンドは1つずつ実行し、`&&` でつなぎません。**

```
git add plugin/renderer
git commit -m "日本語のメッセージ"
```
メッセージの末尾には、次の行を付けます（`-m` を2つ続けて指定できます）。

## 終わるとき
1. 最後の HTML とスクリーンショットを `night-logs/` に残す
2. `docs/night/renderer-visual-report.md` を書いてコミットする。内容は次のとおり
   - `npm test` の結果（件数）と、撮影の検査の結果
   - 見直しの回ごとに見つけて直したこと（最低3回分）
   - 仕様と違えたところと、自分で決めたこと
   - **確認できていないこと。** 実機の iPhone、OneDrive のプレビューでの見え方など、見てほしい点を具体的に挙げる
   - 通せなかったテストがあれば、その理由
3. 全テストが通り、見た目にも満足したら、手を広げずに止まる
