# 夜間の作業：追加4社の評価データの点検

あなたは評価データの点検担当です。作成した担当とは別の立場で、**データそのものを読んで**問題を探します。ファイルは直しません。依頼者は寝ていて、質問には答えられません。最初に `CLAUDE.md`、`docs/design.md`、`docs/night/eval-sets.md` を読んでください。

## 点検の対象
`eval/sets/kuzuri/`、`eval/sets/kinodoten/`、`eval/sets/rater/`、`eval/sets/kenaga/`。形式の検査はテストで済んでいるので、**機械では分からない問題**に集中します。

## 確かめること
1. **正しい記述が本当に正しいか：** すべての主張が、挙げられた根拠の中身で裏づけられるか
2. **誤りが意図どおりの誤りだけか：** 記述に、意図しない別の誤りが混ざっていないか。期待判定は優先順（危険 > 矛盾 > 根拠なし > 正しい）に合っているか
3. **E4 が純粋か：** 調査データや聞き取りのどの事実とも矛盾しないか。矛盾するなら期待判定と合わない
4. **データの内部の矛盾：** 調査データ、聞き取り、業者の情報が食い違っていないか
5. **空白の正解：** `answers/gaps.json` の状態が、調査データから実際に言えることと合っているか
6. **T1〜T5：** 正しい行動と連絡先が、聞き取りと調査データから導けるか
7. **難しさ：** オコジョ精工と比べて、誤りが見え透いていないか。ヒントになる語や、偏りがないか
8. **架空性：** 実在しそうな製品名、会社名、人名が日本語で書かれていないか

## 報告
2つのファイルに分けて書きます。ダミーの認証情報の値は書き写しません。

- `night-logs/eval-sets-review-tuning.md`：`kuzuri`、`kinodoten` の問題。記述 ID、問題、直し方の案、重要度（高、中、低）
- `night-logs/eval-sets-review-holdout.md`：`rater`、`kenaga` の問題。同じ形式。**このファイルは開発の作業で読まないので、依頼者向けに書きます**

問題がなければ「問題なし」と書きます。推測で問題を作らず、根拠 ID を示せるものだけを挙げます。

`npm test` と `git log` のほかにコマンドは使いません。データ、テスト、プロンプトは変更しません。
