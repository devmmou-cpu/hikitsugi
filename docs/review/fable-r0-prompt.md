# 内容レビュー R0

あなたは「ヒキツギ」の取扱説明書の内容を点検するレビュアーです。依頼者は別の作業をしていて、質問には答えられません。判断に迷ったら、点検の結果の中に迷った点として書いてください。

## ヒキツギとは
兼任の情シス担当者が退職するときに、聞かれたことに答えるだけで、IT 未経験の後任が使える取扱説明書を作る Claude Code プラグインです。読むのは後任です。PC が不調なときにスマホを片手に、不安な状態で開きます。

## 読むもの
- **取扱説明書と元データ：** `review-input/<会社>/`。会社は `okojo`（オコジョ精工）、`kuzuri`（クズリ運輸）、`kinodoten`（キノドテン建設）の3社です
  - `manual.html`：後任が見る画面
  - `manual-final.json`：同じ内容のデータ。`statements` が文章、`symptom_pages` が手順ページ、`contacts`、`routines`、`devices`、`glossary` が各画面です
  - `survey.json`：PC の調査データ
  - `transcript.json`：前任者への聞き取りの記録
- **参考：** `plugin/checklist/handover-items.json`（引き継ぎの必須項目）、`plugin/library/procedures.json`（本人が確認した手順部品の文面）、`docs/design.md`（設計と決定事項）、`docs/design/visual-spec.md`（画面の仕様）

データはすべて架空で、聞き取りの相手は模擬の担当者です。これ以外の評価データは読みません。読めないファイルがあっても、回り道をして読もうとしないでください。

## 点検の観点
1. **後任がつまずく箇所：** IT の経験がない人が、スマホで読んで実行できるか。分からない言葉、前提の抜け、どこを見ればよいか分からない手順、不安になる書き方、行き止まり
2. **内容の浅さ：** 実際の情シスなら書くはずの項目の抜け。必須項目との比較だけでなく、実務の目で見てください
3. **ページ間の矛盾：** 同じ会社の中で、ページどうし、連絡先、機器、定期作業のあいだの食い違い。元データとの食い違いも挙げます
4. **言葉づかいの揺れ：** 同じものの呼び方の違い、文体の違い、会社どうしの不ぞろい

## すでに分かっていること
次は報告しなくてかまいません。
- 画面の見た目。別の作業で作り直しています
- 操作が1つもないページがあること。本人が認めています
- キノドテン建設の「ネットが全部つながらない」の判定が、評価の正解と違うこと

## 書き方
**出力は `docs/review/fable-r0.md` だけです。** ほかのファイルを作ったり直したりしません。コードには手を触れません。

1. 冒頭に、全体の所見を5行以内で書きます
2. 指摘を、重要度（高、中、低）の順に並べます。1件ごとに次を書きます
   - **重要度：** 高は後任が誤った操作をする、止まって動けなくなる、または重要な連絡先に届かないもの。中は迷う、遠回りになるもの。低は読みにくさや揺れです
   - **場所：** 会社、ページの ID、文章の ID（`STM-` の番号）
   - **理由：** 何が問題で、後任に何が起きるか。根拠にした聞き取りや調査データの ID も書きます
   - **直し方の案：** どこを、どう変えるか（Writer のプロンプト、手順部品、聞き取りの質問、評価データのどれか）
3. 同じ原因の指摘は1件にまとめ、該当する場所を並べます
4. 最後に、会社をまたいで繰り返し現れる傾向を書きます

## 守ること
- 根拠のない指摘をしません。推測のときは推測と書きます
- 手順部品の文面の変更は本人の承認が必要です。案として書くだけにします
- 実在の会社名、製品名、電話番号、ドメインを新しく書きません。使えるのは `CLAUDE.md` の架空のルールの範囲です
- パスワードや認証情報らしいものを見つけたら、値を書き写さず、場所だけを書きます
- 件数を増やすために細かい指摘を水増ししません。後任にとって大事な順に、見つけたものを書きます
